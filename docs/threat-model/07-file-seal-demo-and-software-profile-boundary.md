# 07 — File-Seal Demo and Software-Profile Boundary

## Built / true today

Reference: `docs/file-seal/file-seal-claim-boundaries.md` is the authoritative claim
boundary document. This doc applies it to the demo/UI context specifically.

### What the demo demonstrates (safe claims)

- Sealing a file into a detached sidecar (`*.andna-seal.json`).
- Sidecar inspection (structural check only; does not imply ACCEPT).
- R1 authenticity verification using the real ML-DSA-44 verifier (liboqs path).
- File-unchanged check (manifest hash comparison).
- R2 authorization against a self-generated local registry snapshot.
- ACCEPT verdict: AUTHENTIC + UNCHANGED + AUTHORIZED — all three explicitly true.
- REJECT verdict: isolated by `unchanged_detail` (file_hash_mismatch, manifest_hash_mismatch)
  or by R1 rejection (signature_invalid) or by R2 rejection (no_registry_entry, etc.).
- Evidence output as a `andna-seal-evidence-v1` JSON file.
- Evidence display in the demo UI (read from the CLI-produced JSON).

### Demo UI architecture

The demo UI is a thin Python/Streamlit shell. It:
- Calls the Rust CLI as a subprocess.
- Displays the JSON output produced by the CLI.
- Contains no verification logic of its own.

**The authoritative engine is the Rust CLI path.** The UI is a presentation layer. A decision
displayed in the UI is only as trustworthy as the CLI binary it called and the process
environment it ran in.

### Software-profile sealer boundary

`init-sealer` (the `SoftwareProfileSigner` in the Rust layer and its CLI wrapper) is
demo/MVP scoped:

| Allowed statement | Disallowed statement |
|---|---|
| Generates local seed material | Generates hardware-backed keys |
| Generates local device identity | Prevents cloning or physical extraction |
| Writes a local software-profile JSON | Is production IAM or HSM custody |
| Enables local seal/verify demonstrations | Proves physical possession |
| Must be protected by the operator | Is a substitute for a hardware security module |

The local profile file holds seed material in plaintext (protected only by filesystem ACLs).
An adversary with access to the profile file has the full signing capability of that sealer.

### Authorization verdict in the demo

The demo registry is self-generated by the sealer: the sealer writes its own `te_hash` into
the registry. The AUTHORIZED verdict in the demo demonstrates the mechanism — that R2 can
evaluate authorization against a registry snapshot and produce a deterministic result — not
that an independent third party approved the device.

AUTHENTIC and UNCHANGED carry independent meaning:
- AUTHENTIC: the ML-DSA-44 signature over the frame is valid.
- UNCHANGED: the file bytes produce the same hash as at seal time.
These two verdicts do not depend on the registry.

### What the demo does NOT do

- Does not encrypt files.
- Does not prove hardware identity.
- Does not prove a human personally reviewed the artifact.
- Does not provide FIPS-validated or ACVP-tested cryptographic primitives (ACVP lab
  engagement is ongoing; not yet complete).
- Does not replace Sigstore, SLSA, TUF, or in-toto.

## Manual checklist (for PR description — no automated UI tests)

Reviewers should verify the following manually in the demo UI before approving:

- [ ] Seal → Verify → ACCEPT: a freshly sealed file verifies as AUTHENTIC + UNCHANGED + AUTHORIZED.
- [ ] Seal → Tamper file bytes → Verify → REJECT (UNCHANGED: no, file_hash_mismatch).
- [ ] Show Evidence: evidence JSON displays deterministic + runtime sections; digest field present.
- [ ] No temp artifacts in repo: `git status --short` shows no `.andna/` or generated evidence files.
- [ ] No verification logic in `app.py`: the UI does not contain an `if signature is valid` branch.

## Not yet built (future mitigations / out of demo scope)

- Hardware-backed sealer (TPM / SE key storage).
- Externally-signed registry (registry entries signed by an authority other than the sealer).
- Demo UI with certificate pinning or process integrity checks.
- Multi-user demo with distinct sealers authorizing each other's artifacts.

## Reviewer questions

1. The AUTHORIZED verdict in a self-provisioned demo registry is structurally correct but
   semantically circular: the device authorized itself. Should the demo registry include a
   second, distinct sealer to demonstrate cross-device authorization?
2. Should `app.py` include a visible disclaimer ("Verification is performed by the andna CLI,
   not this UI") in the interface, not just in this document?
